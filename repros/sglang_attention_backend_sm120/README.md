# SGLang RTX6000 Pro Blackwell FP8 Attention Backend Reproducer

Goal: reproduce and diagnose SGLang attention/backend/shared-memory behavior on RTX PRO 6000 Blackwell / SM120, especially for FP8 hybrid GDN / Qwen3-Next-style models.

## Current public anchor

`sgl-project/sglang#16816` reports that Qwen3-Next-80B-A3B-Instruct-FP8 on RTX6000 Pro Blackwell fails with Triton attention because the Triton backend assumes server-size shared memory around 114k while RTX6000 Pro has a lower hardware limit around 99k/101376 bytes. The issue reports FlashInfer can work with backend-selection changes.

## What this repro must collect

- exact SGLang commit/version,
- exact model path/ID,
- selected attention backend,
- selected linear-attention backend if applicable,
- selected FP8/FP4 GEMM backend,
- hardware shared-memory limit,
- requested shared-memory size if Triton fails,
- warning/error logs,
- correctness sanity output,
- GPU status before/after,
- benchmark result if a server launches.

## Run pattern

```bash
python scripts/run_with_gpu_lock.py --gpus 0 --min-free-gb 70 --wait --label sglang_fp8_triton -- \
  bash repros/sglang_attention_backend_sm120/run_repro.sh \
    --model Qwen/Qwen3-Next-80B-A3B-Instruct-FP8 \
    --attention-backend triton \
    --fp8-gemm-backend triton \
    --linear-attn-decode-backend triton \
    --linear-attn-prefill-backend triton
```

FlashInfer decode fallback variant:

```bash
python scripts/run_with_gpu_lock.py --gpus 0 --min-free-gb 70 --wait --label sglang_fp8_flashinfer_decode -- \
  bash repros/sglang_attention_backend_sm120/run_repro.sh \
    --model Qwen/Qwen3-Next-80B-A3B-Instruct-FP8 \
    --attention-backend flashinfer \
    --fp8-gemm-backend flashinfer_cutlass \
    --linear-attn-decode-backend flashinfer \
    --linear-attn-prefill-backend triton
```

The FlashInfer variant intentionally keeps GDN prefill on Triton. Current
upstream comments indicate FlashInfer GDN support on SM100+ is decode-only.

## Output files

Each real run writes under the GPU wrapper run directory:

- `verify_blackwell.json` with `--probe-cuda` device properties,
- `command.txt`,
- `server_stdout.log`,
- `server_stderr.log`,
- `bench_raw.jsonl` if the server reaches ready state,
- `bench_summary_stdout.json` if benchmarking runs,
- `backend_grep.txt`,
- `backend_summary.json`,
- `status.txt`.

`backend_summary.json` is generated by
`scripts/extract_sglang_backend_evidence.py` and records backend log hits,
linear-attention decode/prefill choices, shared-memory requested/limit values
when present, and failure classes.

## Expected result categories

- `upstream_fixed`: current SGLang accepts and correctly runs backend; document evidence.
- `triton_shared_memory_failure`: failure reproduced with requested vs hardware limit.
- `flashinfer_path_valid`: FlashInfer path works; document correctness/perf and patch path if needed.
- `blocked`: model access/install/hardware constraint; document exact blocker.
